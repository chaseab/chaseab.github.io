OCHE

A DIY autodart scoring rig

Multi-camera vision on a Raspberry Pi finds where each dart landed, turns three views into one hit in millimetres, and streams it to a terminal-brutalist 501 scoreboard. The vision pipeline and the scoreboard are built and tested on their own — wiring the camera to the board is the last mile.

// the throw pipeline

Three cameras in, one number out — and only one direction of flow.

A dart lands. Each camera sees it from a different angle; per-camera homography maps pixels to the board plane, the views are fused into a single coordinate in millimetres from the bullseye, and the board geometry decides what that coordinate scored. From there it's just events: the UI never mutates the match — it replays a log, so undo is "drop the last dart and replay."

01 · SENSE3× camera

Pi cameras, overlapping views of the board.

02 · WARPHomography

Pixels → board plane, calibrated per camera.

03 · FINDDetect

Locate the dart tip in each frame.

04 · FUSEFusion

Three views → one (x, y) in millimetres.

05 · SCOREBoard geometry

coordToSegment — the authority on the hit.

06 · SHOWScoreboard

Event → reducer → state → render.

The wire contract is the seam. Everything upstream — real rig or simulator — converts into the same event type, so nothing downstream knows or cares whether a camera or a Gaussian-scatter sim produced the hit.

// what's built

Build manifest — solo

  • 01 · VISIONMulti-camera pipeline

    Homography, detection and fusion in Python/OpenCV, running on a Raspberry Pi with a systemd service. Covered by pytest.

  • 02 · GEOMETRYBoard in millimetres

    coordToSegment is the single source of truth for what a dart hit — real hardware and the sim both defer to it.

  • 03 · RULES501 engine, pure

    Bust, double-out, legs and sets — no framework, no React. Just a reducer over an event log.

  • 04 · SOLVERCheckout finder

    Computes the finish path instead of shipping a 170-row lookup table. The suggestion panel and the sim aim with the same solver, so they never disagree.

  • 05 · ARCHITECTUREReplayable event log

    feed → events → reducer → state → render, one direction only. The whole match is a log you can replay; undo is dropping the last event.

  • 06 · HARDWARECamera mount, iterated

    SolidWorks-designed, 3D-printed mount taken through four revisions (on-board and off-board variants) to get the geometry rigid and the angles right.

// honest status

What's live, and what's the last mile

Built & tested

  • Multi-camera vision pipeline (homography → detect → fuse), unit-tested
  • 501 double-out scoreboard: rules, checkout solver, live stats
  • Simulated thrower with realistic scatter (PRO / CLUB / PUB)
  • Raspberry Pi capture service + camera calibration
  • Four-revision 3D-printed camera mount

Not wired up yet

  • The rig-to-scoreboard adapter (wsFeed) is still a stub
  • End-to-end camera → live score has not run as one loop
  • Mobile / TV layout (laptop was the first target)
  • Game modes beyond 501 (the domain is shaped for it)

I'd rather show this honestly: the hard, separable pieces work and are tested, but I haven't yet closed the loop from a real dart in the board to a number on the screen. That last integration — normalising the rig's frame schema into the one event type everything already speaks — is the next thing I build.

// what I'm taking from it

Make the seam a contract, and the hardware stops mattering.

  • One event type at the seam. Real cameras or a simulator both collapse into the same wire contract, so I built and tested the whole scoreboard before the rig existed.
  • Compute, don't tabulate. The checkout solver derives the finish path — reusing it for the sim's aim means the demo and the suggestion can never drift apart.
  • Geometry deserves one owner. Everything that needs to know "what did that dart score?" asks the same millimetre-space function. No second opinion.
