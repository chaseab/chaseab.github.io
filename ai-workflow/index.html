How I work with AI

Most of what is on this site was built with an AI assistant in the loop, and I would rather say that plainly than have someone wonder. What follows is which parts that applies to, and the tooling I ended up building around it. The tooling is the part I am actually proud of: the model is the cheap bit, and everything interesting is in what you put around it so it runs unattended without lying to you or breaking something.

What is AI-assisted here, and what isn't

Assisted: most of the code on this site, a lot of the glue code in my projects, the first draft of write-ups, and the harnesses and scripts described below.

Not assisted: the hardware. The wiring, the crimps, the printed parts, the bench tests, the calibration runs, and every number quoted on any project page. Those came off equipment I set up and measured myself.

The rule I hold to: I do not publish a number I cannot reproduce, and I do not publish a claim I cannot defend in conversation. When a page here says something is unmeasured, that is because it is unmeasured.

Two machines, one work queue

I work across a laptop and a desktop, and the desktop has the GPU. They sit on a private network, so either machine can start an agent on the other, hand it a task and get told when it finishes. Work lands in an inbox directory rather than a shared drive, because the two machines do not share a filesystem and pretending otherwise causes exactly the bugs you would expect.

The practical effect is that a long job runs on the machine that should run it, not the machine I happen to be sitting at. One command spawns the session on the far box in the matching directory for whatever repository I am in, and I talk to it from here.

Private networkBoth machines on one tailnet. SSH is firewalled to that network only, so nothing is exposed to the internet.
Spawn and taskAn agent starts on the far machine and receives its work as a message, which avoids mangling long prompts through shell quoting.
Handoff by inboxFiles move to a known directory and the task says where they are. No shared mount, no sync conflicts.
Repository mapEach project knows its counterpart directory on the other machine, so the same command works from anywhere.

A power guard, after losing a drive to one

Twice I started a CUDA training run while the laptop was on battery. A 4070 laptop GPU under load draws more than the pack can source; the rail sags and the machine dies instantly. The signature in the event log is the one that tells you it was not software: a kernel power event with no bugcheck code, no memory dump, no hardware error logged. The first time it corrupted a write in progress and the SSD was replaced.

So now nothing heavy starts without checking, and nothing long runs without assuming it will be interrupted:

  • Any GPU job, long compile or sustained multi-core run checks for mains power first and refuses to start on battery.
  • Every long job checkpoints per step and supports resuming, on the assumption that losing more than one step is a bug.
  • Battery state is polled during a run, because I can unplug it mid-job; on losing mains it checkpoints immediately and throttles.
  • The check is a direct system call, not a shell query in a loop, so it costs nothing to run often.

Gates, so an unattended agent cannot ship something broken

For competition work the failure mode is not a crash, it is a submission that looks fine and is not. So shipping goes through a gate that refuses rather than an agent that tries its best:

  • A pre-flight reads the run's own logs and checks the invariants — the right GPU actually attached, the expected library versions, the inputs mounted, the agent actually fired. A silent fallback to the wrong hardware is a real failure mode and it does not announce itself.
  • It refuses outright if a previous submission is still pending or the daily quota is spent, because both burn the slot.
  • Every attempt appends to a ledger, so the record of what was tried and what it scored is written by the process rather than remembered afterwards.
  • A separate watcher polls for the states that need a human: stuck pending, completed with a blank score, errored, quota nearly gone.

The scheduling is the same shape of problem. The evaluation queue is load-dependent, so runs get built and queued ahead of time and fired into the quiet window rather than whenever they happen to be ready.

This site has the loop wired into it

The most useful thing I built is the least impressive-looking. Every page here has a notes panel: I leave feedback on the page I am looking at, and it saves to a store behind a key. A watcher polls it, waits until I have stopped writing for five minutes, and only then hands the whole batch over — so a burst of six notes is one interruption instead of six.

Notes stay in that panel until they are actually dealt with, at which point they move to a history view: green for handled, yellow for not, and the original text kept verbatim so nothing gets quietly reworded. A separate audit diffs everything I have written against everything filed, which is how I found twenty-one notes that had been read and never acted on.

The other half is this: adding content to a page must not mean rewriting the page. Every project page renders a list of blocks — a video, a figure, a measured result, a dated note — from its own file. Adding one appends an object to that file and touches no prose, so I never have to re-read a page to check that the voice or the facts survived an edit.

What I have learned to insist on

  • Refuse rather than guess. A gate that stops is worth more than an agent that improvises.
  • Verify against the artefact, not the summary — read the log, check the file, fetch the live page.
  • State is on disk. Anything that matters gets written down where the next session can find it.
  • Keep the expensive context out. Screenshots and long outputs go to a sub-process that returns a paragraph.
  • Say what is unmeasured. The moment a page starts rounding up, none of it is worth reading.
